## 0. 사전 절차 (진단 시작 전, 순서대로)

1. **프로필 확정** — §7 표의 슬롯을 대상 프로젝트 값으로 채운다. 못 채우는 슬롯은 사용자에게 확인한다.
2. **기존 기각 기록(fence) 정독** — 프로필에 지정된 기존 audit 기록·기각(⊘)·N/A 확정 결정을 먼저 읽는다. 이미 기각된 claim은 재보고하지 말고 fence 참조로 처리한다. 기록이 없는 시스템이면 "fence 없음, 전부 신규"를 보고서에 명시한다.
3. **정본 보고서 파일 생성** — 프로필의 산출물 위치에 `full-diagnosis-<YYYY-MM-DD>.md`를 만든다. 이 파일이 정본이고, 채팅 출력은 요약이다. 세션 스크래치패드는 소멸하므로 도구 산출물(의존 그래프 등)도 이 파일에 붙이거나 같은 위치에 저장한다.
4. **파일 인벤토리** — 제외 경로(프로필)를 뺀 전체 파일 목록·줄수를 산출해 보고서 커버리지 섹션의 분모로 박는다. 어떤 순서로 읽을지 계획을 사용자에게 보고한 뒤 시작한다.
5. **(이 repo에서 실행 시)** `docs/runtime-audit-instructions.md`(L2.5 v2 정본)를 정독한다. §4는 그 요약이다 — 충돌하면 정본이 우선.

## 1. 절대 원칙

1. **추측 금지.** 파일을 실제로 읽는다. 파일명·함수명만 보고 내용을 추측하지 않는다. 모든 지적에 `파일경로:줄번호` 앵커를 붙인다. 앵커 없는 지적은 무효 — 제출하지 않는다. (여러 파일에 걸친 구조 지적은 대표 지점 앵커 + 관련 지점 열거로.)
2. **거짓 완료 금지.** 다 읽은 척하지 않는다. 커버리지를 3단으로 정직 보고한다: **완독**(전체 정독) / **부분 정독**(구간 명시) / **패턴 스윕만**(grep 스윕, "완독 아님 — 결함 잔존 가능" 명시). 남은 범위는 보고서의 "다음 이어가기" 섹션에 정확히 기록한다.
3. **인상 평가 금지.** "전반적으로 괜찮아 보임" 류 금지. 발견한 사실만 보고한다.
4. **진단 전용 — 코드 수정 금지.** 단 **read-only 실측은 수정이 아니며 오히려 의무에 가깝다**: 재현 가능한 결함은 시나리오 작문으로 끝내지 말고 읽기 전용 호출·사본 데이터·일회성 스크립트로 1회 실측을 시도한다. **사용자 데이터를 변이시키는 재현은 절대 금지** (destructive 재현이 필요하면 시나리오만 적고 "실측 불가 — destructive" 명시).
5. **동작 변경 금지선.** 기존에 *의도대로 작동 중인* 동작을 바꾸는 변경은 어떤 명목으로도 일반 항목으로 제안하지 않는다 — 필요하면 **[동작 변경 제안]** 항목으로 분리해 무엇이 어떻게 바뀌는지 명시한다. **축2 (A) 실제 결함의 수정은 이 금지선의 대상이 아니다** (잘못된 동작→의도된 동작 복원은 "통과하던 동작"이 아님).
6. **"발견 0건 / 해당 없음 / 안전함"도 claim이다.** 그렇게 닫으려면 (a) 사유를 외부 anchor(측정 0건 / 부재를 보인 grep·file:line / 구조적 불가능)로 바닥내고 (b) 그 사유가 틀렸을 반례를 1회 진지하게 만들어본다. 반례가 만들어지면 다시 열고, 못 만들면 자신 있게 닫는다. "안 보임 / 충분히 봤음"은 사유가 아니다.
7. **확신도 메타 명시.** 모든 항목에 명백 / 의심 / 모호 중 하나를 단다. 사용자 우선순위 결정의 핵심 입력이다.
8. **즉시 보고.** 데이터 유실급(High) 발견은 전체 스윕 완료를 기다리지 않고 발견 즉시 사용자에게 보고한다. 멀티턴 스윕 동안 잠재우지 않는다.
9. **결과 예측 발화 금지.** "아마 깨끗할 것" 같은 사전 예측을 컨텍스트에 박지 않는다. 결과는 정독 후 보고만.

## 2. 점검 4축 (판정 기준 — 임의 기준 사용 금지)

### 축 1 — 코드 단순화
- 목표: **분기 / 상태 / 의존성의 감소.** 줄 수 감소가 아니다. 줄만 줄고 인지 복잡도가 같으면 단순화가 아니다.
- **동작 동일성 증명 의무**: ① 제거하려는 코드가 처리하던 입력 경우(엣지케이스 포함)를 전부 나열하고 ② 새 코드가 각각을 어떻게 처리하는지 1:1 매핑한다. ③ 매핑 안 되는 경우가 하나라도 있으면 "동일"이 아니다.
- 매핑이 안 되지만 가치가 커 보이는 재작성은 버리지 말고 **[완화 모드 후보]** 라벨로 분리 보고한다 (내부 패턴 통일 + 사용자 보는 동작 최대한 동일 + 미세 상황 차이 가능 — 채택은 사용자 명시 승인만).
- 각 단순화 항목에 **동작 고정 수단**(프로필의 검증 수단 — 게이트/일회성 round-trip 스크립트 등)을 명시한다. 테스트 인프라가 없는 프로젝트에 "테스트 작성"을 보일러플레이트로 달지 않는다.

### 축 2 — 기존 코드 강화
- **(A) 실제 결함**: 특정 입력에서 잘못된 결과 / 크래시 / 유실 / 누수. **재현 시나리오(입력→예상→실제) 필수** + 가능하면 read-only 실측(§1-4). 재현을 구성하지 못하면 (A)가 아니다.
- **(B) 견고성**: 지금은 안 터지지만 가정이 깨지면 터지는 지점. 의존하는 **암묵 가정**(타입 / 순서 / 전역 상태 / 외부 응답 형태 / 이벤트 도달)을 명시한다.
- 취향·스타일 개선은 보고하지 않는다.

### 축 3 — 코드 누적층 (결합도·취성)
- **순환 의존은 도구로 전수 산출한다** (프로필의 의존 그래프 도구 — JS/TS는 madge, Python은 pydeps 등). 눈으로 추측한 의존성은 "신뢰도 낮음" 표시. 도구 산출물은 정본 파일에 보존한다(§0-3).
- **blast radius는 상위 K(기본 5)만 서술한다.** 전 모듈 전수 서술 금지 — 출력 폭발 대비 가치가 없다(실전 검증됨). 나머지는 도구 산출물로 갈음.
- **결합도(연결 수)와 취성(암묵 가정 위의 결합)을 분리하고, 개별 항목 보고는 취성만 한다.** 진짜 문제는 "암묵적 가정 위의 결합"이다 — 예: 동형 컬렉션 이원화에서 한쪽만 지원하는 유틸, 로드 순서 가정, 같은 식별자를 다르게 파생하는 두 경로.

### 축 4 — 의존성 제거 / 성능 개선
- **점검할 의존성 축은 프로필(§7)에서 지정된 것만** 사용한다 (예: 특정 외부 API / 포그라운드 탭 의존 / 특정 데몬). 지침에 하드코딩하지 않는다.
- 제거 제안 전 의무: ① 그 의존성이 현재 보장하는 것 명시 ② 제거 시 보장의 대체물 또는 상실 명시 ③ **"제거"와 "이동/대체"(비동기화·캐싱·로컬 폴백) 구분** 보고.
- **성능 항목은 `측정됨 / 추정` 라벨 필수. 추정 항목은 High가 될 수 없다.** 측정 가능한데 안 했으면 측정부터.
- **병렬화 제안은 대상 작업들이 공유 상태를 안 건드림을 먼저 증명**한다. 증명 없는 병렬화 제안 금지. 병렬화는 결합을 늘려 축 3과 trade-off — 충돌 시 [충돌] 항목으로.

## 3. 상시 병행 점검 (보이면 해당 축과 함께 보고)

- **에러 삼킴**: 빈 catch, `console.error`만 있는 silent catch, 실패를 성공으로 보이게 하는 응답.
- **암묵적 계약 불일치**: 함수가 기대하는 입력 형태와 호출부가 실제 넘기는 형태의 불일치 (Map vs Object, 타입 이원화의 한쪽 전용 유틸 포함).
- **중복 / 표류 구현**: 같은 기능을 다르게 다시 짠 흔적, 같은 정책의 N갈래 포함 집합 표류.
- **죽은 코드** — 판정 5룰 준수: ① claim은 해당 라인 직접 보고 verbatim 확인 ② 사용처 grep 전수 — **동적 dispatch(이벤트 이름 prop / 문자열 selector / lazy import / class name)는 단순 grep에 안 잡힘**, 의심되면 dead 표시 금지 ③ "확실히 dead"는 100% 확신만, 애매하면 별도 분류 ④ 버그성 주장은 재현 경로 명시 ⑤ 모르면 모른다고. 참고: 사용자에게 노출된 stub(버튼이 무동작/거짓 보고)은 죽은 코드가 아니라 **오정보**로 취급 — 위험 등급을 노출 여부로 매긴다.
- **리소스 누수**: 정리 안 되는 파일/소켓/타이머/리스너/자식 프로세스.

## 4. 검증 코어 (요약 — 이 repo에선 L2.5 v2 정본이 우선)

- **순서 강제: 평평한 발견(weight 판단 금지) → 각 발견을 외부 anchor에 해소 → 그 뒤에야 triage.** 발견 단계에서 severity를 같이 적으면 위반이 출력에 보인다.
- 유효한 바닥은 셋뿐: **측정 데이터 / 조건이 해소된 read-code(이 pass에 새로 읽은 file:line) / 명시적 surface(막힌 링크+내 한계 명명).** "내가 충분히 봤음 / 예상과 일치함"은 바닥이 아니다 — 인용이 검증이 아니라 장식이 되는 걸 막는다.
- **적대적 break-finding**: "안전 / 보존 / bounded / 멱등"류 주장은 default를 "깨진다"로 두고 깨지는 시나리오를 먼저 만든 뒤, 못 일어남을 코드로 보인다.
- **teeth-1 (조건부 실행)**: 인용한 코드가 분기/핸들러 안이면 그 발동 조건이 지금 시나리오에서 성립하는지 해소하는 링크를 반드시 잇는다.
- **teeth-2 (실패 경로)**: 인용한 코드가 실패 가능한 연산(I/O·저장·외부 호출)이면 "성공하나 → 실패하면 어디서 잡히나(삼켜지나) → 실패 *후* 코드가 뭘 하나"까지 잇는다.

## 5. severity / triage

- **severity = 피해 축 × 발동 조건.**
  - 피해 축 서열: **사용자 데이터 유실·손상 > 사용자 조작으로 밟히는 크래시·오정보 > 장기 운영 안정(누수·누적·무한 성장) > 성능 > 유지보수 부채.** (환경별 구체 페인은 프로필에서 보강.)
  - 발동 조건: 통상 조작 1회로 밟히나 / 특정 조합에서만 / 극단 조건에서만. **"통상 조작 1회 + 자가 복구 불가"가 High의 전형.**
- **no-waiver**: 모든 발견은 Q1(즉시 fix 권장) / Q2(설계 논의 필요) / Q3(사소하지만 fix — "Low라 불필요"는 금지된 닫기) / Q4(trade-off라 사용자 결정, 명시 근거와 함께 defer) 중 하나. **severity가 발견을 삭제하지 못한다.**
- **fence(단일 사용자·순차 실행·cap 등 환경 제약)는 severity를 낮추는 데만 쓴다** — fence로 발견 자체를 지우지 않는다.
- **목표 충돌 시 우선순위: 정확성 > 견고성 > 단순함 > 성능.** 충돌 발생 사실 자체를 **[충돌]** 항목으로 분리 보고한다 (어떤 두 목표가 부딪혔고 어떻게 판단했는지).

## 6. 산출물 규약

- **정본 = 파일** (§0-3). 채팅에는 요약(High 전체 + Med/Low 개수 + 커버리지 + 다음 이어가기)만.
- **finding ID**: High는 `H1, H2…`, Med는 `M1…`(또는 `Med-1`), Low는 `L1…`. 이후 수정 커밋 메시지가 이 ID를 참조한다 — 진단↔수정 추적의 고리이므로 ID는 보고서 수명 동안 불변.
- **항목 형식**:
  ```
  ### <ID> [High/Med/Low] (축 N) <한 줄 제목>
  - 위치: 파일경로:줄번호
  - 문제 / 근거(재현 체인·측정·매핑 — 축이 요구한 증거) / 확신도(명백·의심·모호)
  - 분류: (해당 시) A결함/B견고성, 제거/이동, 결합도/취성, [동작 변경 제안], [완화 모드 후보], [충돌]
  - 수정 방향: 방향만 (코드 금지)
  ```
- **한 발견 = 한 entry.** 여러 축에 걸치면 entry 하나에 축 태그 복수 — 축마다 중복 보고 금지.
- **필수 섹션**: 커버리지(3단, 분모 명시) / High / Med / Low / 축3(순환·blast 상위 K) / **미해결 축(사용자 결정 대기 — 옵션과 trade 명시)** / [동작 변경 제안] 모음 / **권장 착수 순서**(수정 세션용 — 밟히기 쉬움+복구 불가 순) / **다음 이어가기**(멀티턴·멀티세션용: 안 읽은 파일 목록, 미해소 claim).
- 수정은 이 보고서를 소비하는 **별도 세션/턴**이 하나씩 진행한다 — 수정 세션은 재분석하지 말고 이 파일부터 읽는다.
