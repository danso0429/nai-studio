# BG Preserve 순차 목표 계획

작성일: 2026-09-20 KST
개정일: 2026-09-21 KST — 별도 연결 패치와 기존 패치의 좁은 수정을 기본 접근으로 명시
진행 기록: 2026-09-24 KST — G1 root 효과 경합 재현과 구현 순서를 §8에 반영
상태: 목표·세부 과제·완료 조건을 정리한 계획안. 구현 완료 또는 배포 기록이 아니다.

## 1. 목표 순서

1. **G1 — AC와 독립적인 BG Preserve 완성:** 서버가 인수한 지원 대상 요청의 생성·후처리·정상 채팅 저장을 브라우저 없이 완료한다.
2. **G2 — 수정하지 않은 공식 AC와의 호환성 확보:** 별도 연결 패치와 기존 BG·저장·호스트 패치의 좁은 수정으로, 공식 AC를 설치했을 때 기존 기능과 저장 소유권이 충돌하지 않는 지원 조합을 확립한다.
3. **G3 — AC 처리까지 포함하는 서버 완주:** G2의 연결 패치를 바탕으로 공식 AC의 기존 API를 사용해 기억 준비·출력 처리·기억 저장까지 브라우저 없이 수행하는 경로를 먼저 구현·검증한다. AC 자체 변경은 기본 해법이 아니다.

각 목표는 독립적인 검증·전달 단위다. 다음 목표의 본 구현은 앞 목표의 완료 조건을 충족한 뒤 시작한다. 현재 목표의 설계 판단에 필요한 후속 목표의 읽기 전용 조사까지 금지하지는 않는다.

G3의 실패나 보류가 이미 완료된 G1·G2를 미완료로 되돌리지 않는다. 단, 후속 검증에서 앞 목표의 실제 결함이 발견되면 해당 결함과 영향 범위를 별도로 수정·재검증한다.

여기서 범용성은 **BG 핵심 기능의 완료 조건과 배포가 특정 AC 변형판에 의존하지 않는 것**이다. 임의의 브라우저 플러그인을 서버에서 실행하는 범용 런타임을 뜻하지 않는다.

## 2. 공통 경계

- BG의 작업·입력·채팅·효과 저장 소유자는 PocketRisu다. AC의 기억 정책·세션·기억 저장 소유자는 AC다.
- G1·G2에서는 공식 AC JS·Go·스키마를 변경하지 않는다. G3도 동일한 원본을 사용하는 연결 패치를 기본 경로로 삼는다. AC 변경 예외는 아래 §5의 구체적인 차단 근거와 별도 범위 결정이 있을 때만 검토한다.
- 파일을 그대로 둔 채 실행 시 AC 스크립트를 재작성하거나, 수정한 AC를 다른 이름으로 묶거나, AC 검사를 우회한 결과를 원본 AC 호환으로 계산하지 않는다. 호스트가 제공하는 API의 좁은 연결·순서 조정은 AC 내부 함수 교체와 구분한다.
- **별도 연결 패치와 기존 패치 수정은 함께 사용할 수 있다.** AC 전용 연결 책임은 별도 패치에 두고, BG·저장·플러그인 호스트에는 확인된 경계의 호출·관측·중복 방지에 필요한 수정만 추가한다. 수정 규모가 작다는 결론은 소스 조사와 검증 전 가정하지 않는다.
- 기존 AC가 제안된 새 필드나 출처 이름을 거절하거나 무시한다는 사실만으로 AC 수정의 불가피성을 결론내리지 않는다. 기존 계약의 의미를 지키면서 연결 패치가 상태·ID 대응·호출 순서를 소유할 수 있는지도 검증한다.
- AC가 없는 경우, 설치됐지만 비활성인 경우, 활성인 경우, 초기화 또는 연결에 실패한 경우를 서로 구분한다. 관측하지 못한 상태를 미설치나 성공으로 바꾸지 않는다.
- 기존 정상 기능·사용자 설정·custom endpoint·로컬 모델 경로를 보존한다. AC를 몰래 끄거나 기억 없이 실행한 결과를 호환 성공으로 계산하지 않는다.
- 새 추상화는 확인된 두 번째 사용처나 실제 경계가 필요할 때만 추가한다. 기존 BG 코드를 모두 다시 작성하거나 일반 플러그인 프레임워크를 만드는 작업은 포함하지 않는다.
- 서버 요청 인수 전 클라이언트 종료, PocketRisu 프로세스 자체 종료 후 임의 지점의 유료 생성 재개는 기존 목표와 구분한다. 이미 durable한 입력·결과·채팅의 복구는 검증 대상이다.
- 이전 테스트 결과는 같은 소스·환경·계약에 한해 재사용한다. 문서, 단위 테스트, 합성 프로세스, 실제 브라우저, 운영 확인의 증거 수준을 구분한다.
- 이번 계획 수립은 기존 변경 폐기·live 적용·외부 AC 기여·stable release를 수행하라는 지시가 아니다.

### 기본 연결 구조

다음은 우선 검증할 책임 배치이며, 현재 구현 완료를 뜻하지 않는다.

| 구성 | 책임과 경계 |
|---|---|
| BG Preserve·저장 패치 | 입력 인수·생성·후처리·정상 채팅 commit을 소유한다. 요청 구성·응답 수신·저장 확정 등 실제로 필요한 경계만 연결 패치에 제공한다. AC나 연결 패치가 없어도 G1이 성립해야 한다. |
| 별도 AC 연결 패치 | 플러그인 식별·지원 판정, 기존 호스트 훅과 통신의 연결, BG 작업과 AC 요청의 대응, 실행 순서·중복 방지·재조회 상태를 소유한다. 필요한 durable 기록은 기존 operation/receipt 저장 구조를 우선 사용한다. AC의 기억 정책이나 DB 내부 쓰기를 대신 구현하지 않는다. |
| PocketRisu 플러그인 호스트 | 기존 권한·격리·통신 계약을 보존하면서 필요한 등록·호출 경계를 연결한다. AC 전용 처리를 일반 플러그인 전체에 적용하거나 IPC 권한을 우회하지 않는다. |
| 공식 AC JS·Go | 기존 설정 해석·출력 처리·기억 준비·수용 판정·기억 저장의 소유권을 유지한다. 기존 호출과 응답이 지원되는 방식으로 연결되는지 검증한다. |

브라우저의 AC 훅 등록이 서버로 자동 이전된다고 가정하지 않는다. G2의 충돌 조정과 G3의 브라우저 종료 후 서버 실행을 구분하며, 모든 훅을 끄는 방식으로 중복을 막아 필요한 출력 변환까지 누락시키지 않는다. 연결 패치의 설치 여부와 실제 AC의 설치·활성·초기화·지원 버전 상태도 별도로 판정한다.

## 3. G1 — AC와 독립적인 BG Preserve 완성

### 사용자 결과

지원 대상 요청을 서버가 인수하면 사용자가 브라우저를 완전히 종료해도 생성·후처리·해당 채팅 저장을 마친다. 다시 접속하면 일반 채팅 열기로 저장된 답변을 읽는다. 화면 복귀·복구 버튼·결과 ACK가 저장의 시작 조건이 아니다.

### 세부 목표

| ID | 세부 목표 | 산출물·검증 기준 |
|---|---|---|
| G1.1 | 기존 작업 보존과 실행 기준 재정리 | 실제 branch·commit·dirty 변경·installer·live 상태를 확인한다. 진행 중 변경을 보존하고 AC 전용 작업과 BG 공통 작업을 분류한다. 구현 재개용 next-work/handoff/fresh-start 문서를 이 목표 순서에 맞춘다. 후보 분리가 필요하면 새 작업선에서 명시적 경로·변경 단위로 구성한다. |
| G1.2 | 실행·저장 책임 확정 | 요청 인수 → 생성 → 후처리 → 정상 chat/effect commit → 일반 조회 흐름을 하나의 소유권 표로 정리한다. legacy 결과, foreground, streaming/non-streaming, 추가 호출·후처리, 기존 브라우저 전용 경로의 지원 범위를 명시한다. 후속 연결에 필요한 실제 경계를 기록하되 AC 전용 계약이나 연결 패치가 BG 기본 활성화의 필수 조건이 되지 않게 한다. 미리 범용 훅 프레임워크를 만들지 않는다. |
| G1.3 | 서버 저장과 실패 복구 | 본문·metadata·변수·통계·receipt의 durable 경계와 원자성을 확인한다. 저장 실패·응답 유실·동일 요청 재조회·취소 경합에서 부분 저장·중복 답변·효과 재가산·모델 재호출이 발생하지 않는지 검증한다. |
| G1.4 | 입력·순서·충돌·보관 수명 | 현재 C3/C6에 흩어진 BG 공통 과제를 닫는다. 자동 drain, 입력 변환 1회, N→N+1 선행 작업 계보, receipt에 근거한 effect 반영, 편집·삭제·reroll·branch 충돌, owner/result/input/context의 보관·정리 경계를 검증한다. 사용자 변경을 덮는 자동 해결은 금지한다. |
| G1.5 | 일반 클라이언트 연결 | capability 협상, early-send, pending 표시, chat-open/복귀 조회, 빈 로컬 저장소의 결과 채택, 구형 클라이언트 fence를 연결한다. 서버 소유 결과를 브라우저가 다시 저장하거나 실패 시 별도 생성하는 경로를 차단한다. |
| G1.6 | 독립 qualification과 전달 | 변경된 소스의 자동검증·runtime audit·패처 조합 검증을 수행한다. 실제 브라우저 종료 전후와 iPhone 시나리오를 확인하고, 적용 소스·빌드 식별·복구 절차·지원표를 남긴다. AC 후보가 없어도 같은 BG 지원 범위가 성립해야 한다. |

### 완료 조건

1. **실제 브라우저 프로세스 종료 후, 다시 열기 전에** 서버 일반 채팅 API에서 저장 본문과 revision을 확인한다.
2. 빈 로컬 상태의 클라이언트가 같은 결과를 채택하고 본문·변수·통계를 다시 쓰지 않는다.
3. 자동 drain·일반 입력 UI·충돌·보관 수명 등 새 client activation에 필요한 BG 공통 과제가 남아 있지 않다.
4. 실패·재시작 검증은 durable 자료 복구와 유료 실행 재개를 구분하며, 불명 상태를 성공으로 표시하지 않는다.
5. 기존 지원 기능의 회귀 검증과 필요한 실제 기기 확인을 마치고, AC 구현 없이 독립적으로 전달할 수 있다.

H1은 G1의 재사용 증거다. H1 통과나 capability 값 변경만으로 G1 완료를 선언하지 않는다.

## 4. G2 — 수정하지 않은 공식 AC와의 호환성 확보

### 사용자 결과

G1을 적용한 PocketRisu에 공식 AC를 설치·설정해도 기존 AC 기능과 BG의 생성·저장 책임이 충돌하지 않는다. 이를 위한 연결은 패처가 제공하고 AC 원본은 유지한다. 어떤 조합이 지원되는지와 브라우저가 필요한 경계를 사용자 기능 기준으로 설명할 수 있다.

### 세부 목표

| ID | 세부 목표 | 산출물·검증 기준 |
|---|---|---|
| G2.1 | 공식 기준선 고정 | 착수 시 사용할 공식 AC 버전·JS·backend·API·hash를 기록한다. 기존 수정 후보와 섞지 않는다. 고정 버전 검증을 이후 모든 버전에 대한 호환 보장으로 확대하지 않는다. |
| G2.2 | 원래 충돌 재현 | 기존에 지적된 충돌을 실제 hook/caller·입력·payload·결과·저장 시점으로 재현한다. 단순히 브라우저 기능이 서버에 없다는 사실과 기존 기능을 손상하는 충돌을 구분한다. 재현되지 않은 가설은 미확인으로 남긴다. |
| G2.3 | 연결 패치와 좁은 host 수정 | 실제 충돌 경계를 바탕으로 별도 연결 패치의 소유 파일과 BG·저장·호스트의 삽입 지점을 정한다. 기존 AC의 훅 등록·통신·채팅 접근 경로를 재사용해 실행·저장 책임을 연결한다. 필요한 설정·출력 동작은 기존 소유자로부터 얻는 경로를 먼저 검증하고, 비공개 내부 값을 추측한 별도 정책 구현으로 대체하지 않는다. |
| G2.4 | 공식 AC와 조합 검증 | 원본 AC에서 prepare → 실제 요청 반영 → 결과 처리 → chat commit → AC 완료의 지원 경로를 관측한다. AC 미설치/비활성/활성/초기화 중/연결 장애, foreground/BG, streaming/non-streaming, 현재/이전 턴 확정, 복귀·빈 클라이언트, 설정 차이·버전 불일치를 검증한다. 지원을 주장하는 PageFold·PDF 등 기존 결합 기능도 확인한다. 서버에 없는 처리와 실제 충돌을 구분해 G3에 넘긴다. |
| G2.5 | 업데이트·비지원 동작과 전달 | 공식 AC 재설치·업데이트 시 지원 판정, 버전 불일치 안내, 안전한 실행 또는 실행 전 거부를 검증한다. 연결 패치의 적용·재적용·제거와 AC 없는 BG 동작을 검증한다. 통합 미지원 상태에서 AC를 조용히 건너뛰지 않는다. G1 회귀와 실제 사용 확인 뒤 지원 조합을 전달한다. |

### 완료 조건

1. 검증 전후 AC JS·backend·migration이 공식 기준선과 일치하며, 숨은 replacement나 검증 우회가 없다. 공식 AC 자체의 정상 데이터 쓰기는 소스 변경과 구분한다.
2. 약속한 지원 조합에서 기존 AC 동작과 BG 저장 동작이 함께 성립하고, 이중 prepare/complete·저장·실행이 발생하지 않는다.
3. 비지원 조합의 처리 방식이 명시돼 있고, 정상처럼 보이는 기능 누락이나 데이터 손상이 없다.
4. AC 활성 상태에서 브라우저를 종료했을 때 가능한 것과 불가능한 것을 실측으로 구분한다. 완전한 AC 서버 완주는 이 목표에서 거짓으로 보장하지 않는다.
5. G2에서 약속한 사용 방식이 공식 AC로 성립하지 않으면 G2를 완료 처리하지 않는다. 제약과 대안을 제시해 목표·범위 결정을 먼저 해소한다. G3가 맡는 완전한 AC 서버 완주의 미구현 자체는 G2 실패가 아니다.
6. 연결 패치의 소유권·적용·재적용·제거를 검증하고, AC 전용 연결을 제외해도 G1이 성립한다. 코드상 소유권 검토와 패처 조합 검증을 런타임 기능 검증으로 대체하지 않는다.

AC를 끄는 것만으로 통과한 결과나 모든 관련 요청을 거부한 결과는 G2 완료가 아니다. 제한적인 foreground 지원만 가능한 경우에도 그것을 사용자가 요청한 BG 호환성의 동등한 대체물로 취급하지 않는다.

## 5. G3 — AC 처리까지 포함하는 서버 완주

### 사용자 결과

지원되는 AC 설정과 입력을 서버가 인수한 뒤에는 브라우저가 없어도 기억 준비·실제 모델 요청 반영·출력 처리·정상 채팅 저장·설정에 맞는 AC 완료 처리가 이어진다. 기본 구현 경로는 **공식 AC를 그대로 사용하는 연결 패치의 서버 실행**이다. 현재 턴/이전 턴 확정 정책을 유지하고, 다음 입력은 필요한 기억과 효과 반영 경계를 준수한다.

### 세부 목표

| ID | 세부 목표 | 산출물·검증 기준 |
|---|---|---|
| G3.1 | 원본 AC를 사용한 서버 왕복 실험 | 아래 최소 실험으로 G2에서 남긴 브라우저 의존 처리를 검증한다. 기존 공식 API로 준비·결과·완료를 연결하고 실제 브라우저 종료 후에도 이어지는지 확인한다. 제안한 신규 필드가 거절되는 실험만으로 기존 계약의 사용 불가를 판정하지 않는다. |
| G3.2 | 연결 패치의 계약·소유권 확정 | BG 작업과 AC 요청의 ID 대응, 요청별 설정, 인증·버전 협상, 실행 순서·재조회·보관·업데이트·되돌리기 책임을 기존 계약 위에 정의한다. browser/server 및 다른 탭·기기의 직접 호출·설정 변경까지 조정 범위에 들어오는지 확인한다. AC가 BG operation ID를 직접 저장해야 한다고 미리 전제하지 않는다. |
| G3.3 | 연결 패치의 서버 실행 구현 | 실험에서 성립한 경로를 기존 BG 실행·저장 경계에 연결한다. AC prepare·실제 payload 적용·출력 변환·complete의 최종 호출자를 추적하고, 요청별 설정과 기존 우선순위를 보존한다. foreground/BG 출력 및 실제 채팅/AC 저장 후보의 parity를 증명한다. 별도 구현이 필요한 출력 helper는 원본 동작과 버전별 동등성을 검증한다. |
| G3.4 | 장애·수명주기 결합 | AC 응답 유실·재시작·중복 호출·실행 소유권 변경·편집/삭제·취소·이전 턴 확정·skip·late backfill·retention을 검증한다. 연결 패치를 거치지 않는 실제 호출 경로도 확인한다. AC 실패가 BG 본문의 중복 생성이나 이미 저장된 채팅 손상으로 이어지지 않게 한다. 원문 저장과 파생 기억 완료를 구분한다. |
| G3.5 | 독립 연결 패치 전달과 최종 qualification | 브라우저 종료 중 실제 기억 주입·정상 채팅 저장·AC 저장·다음 턴 반영을 확인한다. 원본 AC의 소스·실행물 일치, G1·G2 회귀, 연결 패치의 적용·재적용·제거·버전 호환을 검증한다. 연결 패치가 없거나 AC를 사용하지 않을 때에도 이미 약속한 BG 기능을 보존한다. |

### G3.1 최소 왕복 실험

1. 공식 AC JS·Go·migration의 고정 기준선을 확인하고 격리된 합성 데이터로 실행한다. 기존 수정 후보를 시험 대상에 끼워 넣지 않는다.
2. 기존 AC가 해석한 설정과 실제 요청 정보를 기존 호스트 경계에서 필요한 만큼 얻어 전달한다. 브라우저가 담당해야 하는 사전 준비가 있다면 서버 인수 완료보다 앞에 둔다는 조건과 그 의미를 명시하고 검증한다.
3. 연결 패치가 기존 AC API를 사용해 기억을 준비하고, 실제 주 모델 payload에 적용한 내용을 확인한다. 호출 주체·설정·저장 자료·수용 판정을 함께 기록한다.
4. 고정 모델 응답으로 시작해 서버 인수 뒤 브라우저가 사라진 경계를 검증한다. 먼저 별도 요청 프로세스 종료로 서버 경계를 확인하고 실제 브라우저 프로세스 종료로 증거를 보강한다. 출력 처리·정상 채팅 commit·AC 완료의 내용과 순서를 확인한다.
5. 응답 유실·동일 요청 재조회·복귀 후 기존 AC 훅을 각각 실행해 중복 처리 여부를 확인한다. 현재/이전 턴 확정과 실제 사용 설정으로 범위를 넓힌 뒤에만 해당 지원을 주장한다.
6. 실패하면 입력·기존 API/최종 caller·실제 응답·깨진 사용자 요구·남은 대안을 남긴다. 구현 결함, 선택한 접근의 실패, 기존 계약 자체의 한계를 구분한다.

### 완료 조건

1. 관측하지 않은 브라우저 이벤트를 만들어 보내거나 AC의 수용 검사를 우회하지 않는다.
2. 서버 인수 뒤 브라우저 재접속 없이도 실제 payload 반영·채팅 저장·설정에 맞는 AC 처리 상태를 외부에서 확인할 수 있다.
3. 응답 유실과 재조회가 모델 유료 호출·채팅/effect·AC 원문 및 파생 처리의 중복을 만들지 않는 검증 근거가 있다. 실행 결과가 불명인 경계는 명시적 상태로 남긴다.
4. AC의 설정·provider·출력·확정 정책을 지원 범위에서 보존하고, 다음 턴은 검증된 순서 경계를 따른다.
5. G1·G2를 사용할 수 있는 범위와 G3의 배포·업데이트 책임이 분리돼 있으며, 실제 브라우저·iPhone 확인을 마친다.
6. 기본 경로는 공식 AC 원본과 연결 패치로 qualification한다. AC 변경 예외가 별도로 선택된 경우에는 원본 AC 호환 결과와 구분해 수정 범위·근거·유지 책임을 명시한다.

### AC 변경 예외를 검토하는 조건

AC 수정의 불가피성은 현재 입증되지 않았다. 다음 근거를 갖춘 특정 요구에 한해 변경 예외를 검토한다.

- 수정하지 않은 AC에 대한 positive/negative 왕복 실험과 실제 실패 경로가 있다.
- 어떤 기존 계약으로 어떤 필수 사실·처리·상태를 표현하거나 보존할 수 없는지 설명할 수 있다. 신규 필드 거절, 무시된 operation ID, 미구현 어댑터, 단일 실험 실패만으로는 부족하다.
- 별도 연결 패치, 기존 패치의 좁은 수정, 기존 호스트/API 재사용으로 같은 효과를 유지할 대안을 검토했고, 각 대안이 막힌 지점이나 해결되지 않은 조건을 기록했다.
- 필요한 AC 변경의 최소 범위, 보존해야 할 기존 기능, 상류 업데이트 대응·배포·되돌리기 책임을 제시한다.

이 근거가 마련돼도 자동으로 AC 변형판 개발로 전환하지 않는다. 요구 유지·지원 범위 변경·AC 변경 허용 중 사용자 결과가 달라지는 방향을 결정한 뒤 진행한다. 원본 AC 경로가 막힌 상태를 기능 축소나 수정 후보의 성공으로 덮어 완료 처리하지 않는다.

## 6. 기존 작업의 재배치

| 기존 작업 | 새 목표에서의 취급 |
|---|---|
| C1 서버 commit, C2 BG 결과 연결 | G1의 기반. 현재 소스와 호출 경로가 맞는 범위에서 재사용한다. |
| C3 입력·설정·projection·hydration, H1 프로세스 검증 | G1의 기반과 증거. 일반 client/drain·실제 브라우저 경계를 별도로 닫는다. |
| C6의 BG 공통 effect 계보·충돌·보관 수명 | G1으로 이동한다. AC 완성을 기다리는 조건으로 남기지 않는다. |
| 공식 AC 관측·기존 충돌 조사 | G2의 출발점. 별도 연결 패치와 기존 패치 수정으로 원본 AC에서 재현·검증한다. 수정 후보의 성공으로 공식 AC 호환을 대신하지 않는다. |
| C0의 AC 계약 실험 | 선택한 계약의 실패·필드 무시 등 실제 관측 범위만 재사용한다. 패처만의 연결 불가능이나 AC 변경 불가피성의 증거로 확대하지 않는다. |
| C4/H2의 AC Go 확장 | 참고 구현·증거로 보존하되 G3의 기본 해법에서 제외한다. 원본 AC 왕복 실험에서 특정 계약의 변경 필요성이 입증된 경우에만 해당 부분의 재사용을 검토한다. |
| C5/H3의 AC JS 수정·전용 bridge·출력 변환 | 원본 AC를 수정한 부분과 패처 쪽 연결 부분을 구분한다. 기존 계약으로 사용할 수 있는 연결 코드만 G2/G3 재사용 후보로 검토하고, 수정된 AC export·API를 요구하는 부분은 기본 경로에 넣지 않는다. 설정 owner·실제 caller·출력 동등성을 검증한다. |
| C6의 AC claim/change/prepare/complete/retention | 달성해야 할 효과를 G3에 넘기되 구현 위치를 고정하지 않는다. 연결 패치에서 소유할 상태와 AC에 맡길 기존 처리를 나누고, 새 AC claim/API·스키마를 전제하지 않는다. |
| C7 및 H6/H7 qualification·문서·release 절차 | 각 목표의 실제 변경과 지원 범위에 맞춰 적용한다. G3 전까지 모든 사용자 검증과 전달을 미루지 않는다. |

기존 commit·dirty 변경·증거·source snapshot은 삭제하지 않는다. 새 후보에서 제외하는 작업과 원본을 폐기하는 작업을 구분한다. 모든 결과를 다시 측정하지 않고 변경·모순·새 최종 호출 경로가 생긴 범위에 검증을 집중한다.

## 7. 목표별 완료 기록

각 목표 종료 시 다음 항목을 한 기록으로 남긴다.

- 사용자에게 제공되는 결과와 지원/비지원 조합.
- 정확한 source·installer·AC 공식 기준선 또는 채택한 확장 계약.
- 직접 관측한 자동검증·process/browser·실제 기기 결과와 아직 확인하지 못한 경로.
- 실패·복구·retention·업데이트·되돌리기 절차와 남은 위험.
- 다음 목표에 넘기는 제약 및 필요한 결정. 다음 목표의 조건을 현재 목표의 완료 근거로 사용하지 않는다.

각 목표의 candidate 구현·검증·전달은 기존 저장소 절차를 따른다. Stable tag/release는 해당 사용자 검증과 문서·버전·민감정보 검사를 마친 뒤에만 수행한다. 목표마다 stable tag를 반드시 만들 필요는 없다.

기준 통계 10에서 브라우저와 N이 각각 +1 하면 12가 필요하다. 브라우저 저장이 먼저 끝나면 12였지만, N이 먼저 커밋된 뒤 오래된 브라우저 저장이 patch-sync 또는 조건부 full-write의 충돌 재시도를 거치면 11이 남았다. ETag 없는 오래된 full-write는 10으로 되돌릴 수도 있었다. BG 적용 ledger는 남아 있어 단순 ledger 보존이나 predecessor 값 대조만으로 이 누락을 검출하지 못한다. 브라우저의 +1이 이미 저장됐지만 응답만 유실된 뒤 N이 커밋된 반대 사례에서는 원격 값 12가 맞으므로, 무조건 `remote + (local - base)`로 바꾸면 13으로 중복된다. 구현 전 정상·실패·응답 유실의 root writer와 안정적인 효과 식별 경계를 확정하고, 서버 저장 수용과 클라이언트 재시도를 함께 수정한다. 통계의 가산 효과와 전역 변수의 set/delete 충돌 정책을 섞지 않으며, 기존 foreground·구형 클라이언트·최초 DB 생성 경로를 보존한다.

위 자동 시험은 동일한 최종 소스에 대한 일괄 전수 통과를 뜻하지 않는다. ACK 복구 후속 변경은 집중 시험과 타입 검사로 확인했고, 전체 서버·프런트엔드 시험은 그 직전 후보에서 수행했다. 새 root 진단은 격리 프로세스·합성 provider와 실제 HTTP 저장의 증거이지 실제 브라우저·기기 결과가 아니다. **G1은 아직 완료되지 않았고 live PocketRisu와 공식 AC는 이 후보에서 바뀌지 않았다.** G2 본 구현은 G1 완료 뒤, G3 본 구현은 G2 완료 뒤 시작한다.

**G2/G3의 기본 경로는 별도 연결 패치와 기존 패치의 좁은 수정이며, 원본 AC 왕복 실험보다 AC 자체 변경을 먼저 진행하지 않는다.** 보존된 AC 수정 후보의 성공을 원본 AC 호환의 증거로 계산하지 않는다.

이 문서는 [기존 상세 통합 계획](POCKETRISU-1.10-BG-PRESERVE-SERVER-CHAT-SAVE-ARCHIVE-CENTER-PLAN.md)의 기술 자료를 재사용하되, 그 문서의 통합 일괄 활성화 순서를 새 목표의 완료 조건으로 가져오지 않는다. 현재 문서 작성만으로 기존 실행 문서가 갱신됐거나 진행 중인 다른 실행이 중지됐다고 간주하지 않는다.
